## 8. Generations

**Status.** Checklist. Head revision on main is `carousel_final_assembly`. Implement in the order below. Each box is one commit, and the console still works after that commit. Each box names the tests that land with it. Task 8.9 runs the full suites and `npm run build`.

**Goal.** A generation is a snapshot. Duplicate it to try the next version.

**What the code does today.** `carousels.generation_number` is an integer, not null, server default 1, check `generation_number >= 1`. `create_carousel` stores `CAROUSEL_GENERATION_NUMBER_DEFAULT` (1). There is no generations table. The number is the phase 8 counter and nothing else. Every carousel on main, including Default, is generation 1.

The ops console already shows that number. `generationLabel` in `apps/ops/src/pages/carouselSteps.ts` returns `Generation ${n}`. The open carousel renders it in the header pill `#carousel-generation` (`CarouselGeneration` in `CarouselSectionNav.tsx`; the comment says the page shows "Generation 1" now) and again at `#carousel-basic-generation` in `CarouselBasicStep`. The carousel list has a Generation column. The slide editor repeats the pill and has no duplicate control. There is no carousel duplicate route. `POST /api/v1/skeletons/{skeleton_id}/duplicate` copies a skeleton. It does not copy a carousel.

Instructions are `carousel_instructions`: `position` and `body`, no title and no version. `INSTRUCTION_BODY_MAX_CHARACTERS` is 1,000,000. The body on the row is the current text. The album is `carousels.album_id`, nullable, `ON DELETE SET NULL`. Images live on that album in `album_images.position` order. A slide points at one of them through `slides.album_image_id`. Research is `carousel_research_items` in `position` order. The title and body live on `research_items`. Deleting a research item deletes the link. `CarouselReadResponse.research` returns id, title, slug, and position. It does not return the body.

A slide has `name`, `position`, `text_status` (`draft` or `live`, server default `live`), `album_image_id`, and `draft_batch_id`. Live copy is `slide_element_texts.value`. Unaccepted copy is `draft_value`. Exclusions are `slide_exclusions`, stored in both directions. `slide_draft_batches` is the review state for one press of Generate: `pending`, `accepted`, or `discarded`, one pending row per carousel. The model notes in `app/models/carousel.py` and `app/models/__init__.py` say that table is not the phase 8 snapshot.

Final already keys `carousel_assemblies` by `(carousel_id, generation_number)`. `assemble_carousel_final` copies `carousel.generation_number` onto that row. A later assemble for the same number keeps the row id and replaces `assembled_carousels` and `assembled_carousel_frames`. The PNG path is `assembled/{assembly_id}/{frame_id}.png`. `slide_id` and `album_image_id` on a frame set null when that source row is deleted, and the frame stays. There is no `generation_id` foreign key. `_assembly_response` and `_generation_has_final_assembly` return the assembly whose `generation_number` equals the carousel's number, so a different number is already invisible to the detail and to `steps.final`. `campaign_carousels`, `POST /api/v1/generate/carousel`, and `MockPublishAdapter` are still the old loop. The open carousel is one scrollable page. `editor_step` does not choose the panel.

**Settled for this phase.** The tasks use these. The open decisions at the end are the choices Mu can still change.

- A generation is rows on this carousel, not a second carousel and not a copied skeleton. `name`, `slug`, `skeleton_id`, and `editor_step` stay. `POST /api/v1/skeletons/{skeleton_id}/duplicate` stays as it is.
- The working rows stay the current generation: `carousel_instructions`, `carousels.album_id`, `carousel_research_items`, and `slides`. `carousels.generation_number` is that generation. Writes refresh that generation's snapshot and leave every lower number alone.
- Duplicate refreshes the current snapshot, adds 1 to `generation_number`, and writes the new generation from the same working rows. It does not insert slides, delete slides, or call a provider. It does not drop losers or add slides from winners. Phase 12 is that step.
- The instruction version is the copied `position` and `body`. This phase does not add a version column to `carousel_instructions`.
- The snapshot stores `album_id` and the ordered image ids. It does not copy image bytes. It stores each attached research item's id, position, title, and body.
- Phase 7 frames stay where they are. The new `generation_id` hangs the existing `carousel_assemblies` row on generation 1. Duplicate does not copy that row, its children, or its PNG files. The new generation has no assembly until the next Assemble.
- Nothing in this phase is a post. Duplicate does not read `campaign_carousels`, `artifacts`, `post_jobs`, or metrics. The carousel name is not part of the snapshot. A rename does not refresh it. The caption already stored on an assembled carousel stays there.
- The page stays one scroll. The new control is Duplicate, next to the header pill.

### Open decisions

These are the questions section 8 leaves open. The tasks above use the recommended default so a commit can name a file.

1. **Where slide edits go after a duplicate.** The phase map asks whether slide edits land only on the new generation. Recommended default: yes. The working slides stay the rows the editor writes, and `generation_number` says which generation those rows are. Duplicate freezes the previous generation by writing its snapshot and then stopping later refreshes from touching it. Slide rows are not copied into a second set. A frame from phase 7 keeps its `slide_id`, so that pointer can sit on a slide whose text has since changed. The previous generation is read from the snapshot and from the frozen PNG. Say if the old slides should be copied to new rows and left unchanged, so a frame's `slide_id` still points at text that cannot change.
2. **The shared album.** The phase map asks whether the snapshot stores the album id or the list of images it used. A later upload changes the album behind a shared id. It does not change a copied list. Recommended default: store both. `album_id`, plus the ordered image ids written when that generation was last refreshed. Do not copy the bytes. A later upload does not add a row to a previous generation. An upload while a generation is current is included the next time that generation is refreshed. Deleting an image sets that slot's `album_image_id` null and leaves the position, the same way a frame pointer clears. Say if only the album id should be stored, or if the image ids should be plain UUIDs with no foreign key so a delete does not clear them.
3. **What the instruction version is.** The snapshot is described as the instruction version. `carousel_instructions` has no version column, and phase 5 left it that way on purpose. Recommended default: copy each document's `position` and `body`, including a stored `""`. That copy is the instruction version. Do not add a version column, and do not keep an older body on the instruction row. Say if each save should keep the previous body as its own version.
4. **Whether the research snapshot copies the document.** The snapshot includes the research. The title and body live on the shared library row, and a later edit would otherwise change every carousel that still points at it. Recommended default: copy `research_item_id`, `position`, `title`, and `body`. A later edit does not change a previous generation. Deleting the library item nulls the id on a previous generation and leaves the copied title and body. An empty attachment list stays empty. Say if the snapshot should store only the id and the position.
5. **Whether the operator can open a past generation.** Recommended default: no. The pill, the Basic line, and the list show the current number. Duplicate is the only new control. The single-generation GET is there for a later phase. Final shows the current generation's assembly, which is empty after duplicate until the next Assemble. Say if the page should open a past generation read-only, or show that generation's frames under Final.
6. **When duplicate is allowed, and what happens to a pending set.** Nothing is posted in this phase. The campaign timeline is phase 9. Recommended default: duplicate does not require an assembly, instruction text, or live slides. It does not copy the assembly or the `slide_draft_batches` row. A pending set stays pending on the working slides, so the new generation still shows that review. The previous snapshot records those slides' `text_status`, `value`, and `draft_value`. Say if duplicate should be refused until Final has run, or if it should discard the pending set first.
